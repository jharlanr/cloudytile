cloudy-tile: how it works

A newcomer's guide to the repo, the data, and the network. Last updated August 2026.

1. The problem

Downstream of this repo, the lake-vision classifier watches supraglacial lakes on the Greenland ice sheet through a melt season of Sentinel-2 imagery and decides how each lake drained. Many timesteps in that record are worthless — the tile is under cloud, or the satellite swath missed it entirely. Feeding those frames to lake-vision degrades it, so each frame must first be screened: is this tile usable or not?

The obvious answer — use Sentinel-2's own per-pixel cloud mask — does not work here. Cloud masks are notoriously unreliable over bright ice: fresh snow and cloud look alike to the detector. In our 2019 labels, scenes a human rejected actually carried lower reported cloud cover than scenes they kept. That failure is the reason this repo exists.

cloudy-tile trains a small CNN, CloudyTileCNN, to make the call a human makes in half a second: 1 = useful (clear enough to read the lake, even through thin cloud), 0 = not useful (cloud-obscured or mostly missing data). Its per-timestep predictions are written into each lake's NetCDF as cloudy_seq_rgb, which lake-vision uses as its usability filter.

A tile with visible thin cloud can still be useful: if the lake's extent reads through the haze, it carries information. The label is about usability, not about the mere presence of cloud. This judgment call — thin cloud over bright ice — is the hard part of the task, for humans and for the model.

2. The pipeline

Source imagery is the published ESSD SDR deposit on OAK (data/essd_sdr/data/CW{2018,2019}/: 679 + 1,000 per-lake NetCDF files, 153 daily timesteps each, six Sentinel-2 bands as raw L2A digital numbers). Only the imagery is shared with the ESSD work — cloudy-tile keeps its own labels and its own splits.

3. Data contracts

Two conventions hold the pipeline together. Break either and things fail silently.

contractformexample
frame filename{lake_id}_t{timestep:03d}.jpgCW2019_1530_t006.jpg
labels CSVcolumns filename,label; filename uniqueCW2019_1530_t006.jpg,0

The polarity is load-bearing: 0 = not useful, 1 = useful. It matches CloudyTileDataset's docstring and the cloudy_seq attributes written at inference. The lake id is recoverable from any filename by splitting on the final _t — that single fact is what makes lake-grouped splitting possible.

25 frames per lake, drawn at random across the May–September melt season, keeping only frames whose RGB is <50% no-data (extract_label_frames.py). 2018 was a much cloudier season than 2019, which is why its negative rate is higher — and why the combined set is better balanced than either year alone. Every one of the 400 lakes contains both classes. An earlier 2,090-frame Labelbox campaign over just 60 lakes is retired in labels/labels_deprecated.csv; it must never be merged with the current file, since it labels a different frame population.

4. Splitting: always by lake, never by tile

Two frames of the same lake a few days apart are near-duplicate images. A split drawn at the tile level therefore puts almost every lake on both sides of the line: the model meets the test lakes during training and the test score measures recognition, not generalization. This is not hypothetical — the original tile split of the deprecated dataset put all 52 test lakes in the training set too.

cloudytile/splits.py implements this: create_lake_splits for a single 80/10/10 partition (320/40/40 lakes on the current data), lake_group_kfold for stratified 5-fold CV (80 held-out lakes per fold), and assert_lake_disjoint as a guard. run_training.py defaults to --split_by lake; the legacy --split_by tile survives only to reproduce old runs, and warns.

5. The network

CloudyTileCNN (cloudytile/model.py) is a deliberately small CNN: three conv blocks, each conv 3×3 → ReLU → maxpool /2, followed by a fully-connected head. Input is an RGB frame resized to 512×512, values scaled to [0,1]; output is a single logit (sigmoid → probability of "useful").

Where the 33.5 million parameters come from

The conv stack is tiny (≈23.6k weights). The explosion happens at the boundary between convolution and the head. After three pool halvings, the feature block is 64 × 64 × 64 = 262,144 numbers — and Flatten → Linear(262144, 128) connects every one of them to every one of 128 neurons:

Nobody chose a 33M-parameter model; the dense layer silently inherited the full image area, because a flatten head scales with resolution, not with design intent. Fit to ~8,000 training frames, that is roughly 4,000 parameters per example — ample capacity to memorize the training lakes, which is also why the tile-split leak inflated scores so effectively.

The fix: global average pooling

The planned architecture revision replaces flatten with GAP and adds batch normalization after each conv, dropout before the final layer, and flip/rotation augmentation (satellite tiles have no canonical orientation, so this is a free 8× on the data).

6. Baselines any model must beat

Measured on 40 held-out lakes (1,000 frames) of the current dataset:

baselineaccuracywhat it knows
majority class ("always useful")68.4%nothing
JPG file-size threshold (44 KB)82.5%one byte count per image

The file-size baseline works because JPEG compression is an entropy meter: clear ice is detailed and compresses poorly, cloud is smooth and compresses well (cloudytile/splits.py::filesize_baseline). Any reported CNN accuracy should be quoted against 82.5%, not against chance — the interesting margin is what the network earns above a stat() call. Scene-level eo_cloud_cover metadata, for comparison, is nearly uninformative about per-tile usability and in 2019 actually ran backwards against human judgment.

7. Running it

Extract frames for labeling (Sherlock)

sbatch engine/preprocessing/extract_label_frames.sh
# 200 lakes x 25 frames per year from the SDR deposit, <50% NaN, seeded

Label (local browser GUI)

python3 engine/labeling/label_gui.py --image_dir data/label_frames_2019
# left arrow = 0 not useful | right arrow = 1 useful
# backspace = back one frame | space = forward | h = help with examples
# writes labels/labels.csv atomically after every keypress; resume is automatic

Train

python3 engine/training/run_training.py \
    --labels_csv labels/labels.csv \
    --image_dir data/label_frames_all \
    --optimize_metric loss --save_path best_model.pth
# splits by lake by default; test metrics are computed on the restored
# best-validation checkpoint, i.e. the same weights written to --save_path

Inference over the lake archive

from cloudytile.inference import process_directory
process_directory(nc_dir=..., model_path="best_model.pth",
                  nc_channels=["red","green","blue"],
                  var_name="cloudy_seq_rgb", output_dir=...)

8. Lessons encoded in this repo

  • Split by group, not by sample, whenever samples are correlated — here, frames of the same lake. The guard is one assert; the silent version of the bug costs months.
  • Report the dumb baseline. A file-size threshold scored 88% on the old dataset; nobody knew because nobody computed it.
  • Metrics must describe the artifact. Training now restores the best checkpoint before the test pass, so the printed numbers describe the saved weights.
  • Parameter counts hide in dense layers. Print them per layer once per architecture change; a flatten head scales with image area, not intent.
  • Label many groups shallowly rather than few groups deeply: 400 lakes × 25 frames beats 60 lakes × 35 frames at the same labeling cost.
