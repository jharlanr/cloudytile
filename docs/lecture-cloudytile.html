cloudy-tile: how it works

A newcomer's guide to the repo, the data, and the network. Last updated August 2026.

1. The problem

Downstream of this repo, the lake-vision classifier watches supraglacial lakes on the Greenland ice sheet through a melt season of Sentinel-2 imagery and decides how each lake drained. Many timesteps in that record are worthless — the tile is under cloud, or the satellite swath missed it entirely. Feeding those frames to lake-vision degrades it, so each frame must first be screened: is this tile usable or not?

The obvious answer — use Sentinel-2's own per-pixel cloud mask — does not work here. Cloud masks are notoriously unreliable over bright ice: fresh snow and cloud look alike to the detector. In our 2019 labels, scenes a human rejected actually carried lower reported cloud cover than scenes they kept. That failure is the reason this repo exists.

cloudy-tile trains a small CNN, CloudyTileCNN, to make the call a human makes in half a second: 1 = useful (clear enough to read the lake, even through thin cloud), 0 = not useful (cloud-obscured or mostly missing data). Its per-timestep predictions are written into each lake's NetCDF as cloudy_seq_rgb, which lake-vision uses as its usability filter.

A tile with visible thin cloud can still be useful: if the lake's extent reads through the haze, it carries information. The label is about usability, not about the mere presence of cloud. This judgment call — thin cloud over bright ice — is the hard part of the task, for humans and for the model.

2. The pipeline

Source imagery is the published ESSD SDR deposit on OAK (data/essd_sdr/data/CW{2018,2019}/: 679 + 1,000 per-lake NetCDF files, 153 daily timesteps each, six Sentinel-2 bands as raw L2A digital numbers). Only the imagery is shared with the ESSD work — cloudy-tile keeps its own labels and its own splits.

3. Data contracts

A handful of conventions hold the pipeline together. Break any of them and things fail silently.

contractformexample
frame key{lake_id}_t{timestep:03d}CW2019_1530_t006
labeling frameframe key + .jpg, true-colour RGBCW2019_1530_t006.jpg
training tileframe key + .nc, six float32 bandsCW2019_1530_t006.nc
labels CSVcolumns filename,label; filename uniqueCW2019_1530_t006.jpg,0

The polarity is load-bearing: 0 = not useful, 1 = useful. It matches CloudyTileDatasetNC's docstring and the cloudy_seq attributes written at inference. The lake id is recoverable from any filename by splitting on the final _t — that single fact is what makes lake-grouped splitting possible.

What a training tile contains

Each .nc tile carries all six SDR bands — red, green, blue, nir, swir16, swir22 — as float32 surface-reflectance digital numbers, with NaN marking no-data. Which of the six a run actually uses is a training-time choice (--nc_channels), which is what makes the band question in the config grid answerable without re-extracting anything.

Normalization happens in a specific order, and the order is the whole point: 

nan_mask = np.isnan(imagery)
imagery = (imagery - band_mean) / band_std   # per-band, from band_stats.json
imagery[nan_mask] = 0.0                      # exactly 0.0, in NORMALIZED space

Per-band statistics matter because the bands are not on remotely the same scale: the visible bands average ~8,000 DN with a coefficient of variation of 0.20–0.23, while SWIR averages ~1,350 with a CV above 1.0. Setting no-data to zero after normalizing puts it at the mean of each band — the least informative value available.

Doing it in the other order is what makes this more than bookkeeping. Fill first and a raw 0 DN normalizes to −4.4 σ in red, −4.9 σ in green and −5.1 σ in blue: an extreme, perfectly constant value marking exactly the pixels that carry no information. Since no-data fraction correlates with the label, that hands the network a shortcut feature it can key on instead of learning cloud from ice. (Note the shortcut is far weaker in SWIR, where 0 DN lands at only −0.9 σ — another consequence of that band's much wider spread.)

4. Splitting: always by lake, never by tile

Two frames of the same lake a few days apart are near-duplicate images. A split drawn at the tile level therefore puts almost every lake on both sides of the line: the model meets the test lakes during training and the test score measures recognition, not generalization. This is not a hypothetical risk but an arithmetic certainty. Take any densely-sampled lake set — say 60 lakes with ~35 frames each — and split it at the tile level: whatever the seed, the test tiles touch 56–60 of the 60 lakes and 100% of test lakes also appear in training. With 25 frames per lake in the current set the arithmetic is the same. A tile-level split cannot hold anything out.

cloudytile/splits.py implements this: create_lake_splits for a single lake-disjoint partition, lake_group_kfold for stratified grouped CV, and assert_lake_disjoint as a guard that is called, not merely available. run_training.py defaults to --split_by lake. A --split_by tile option exists but emits a warning: there is no correct use for it on this data.

Freezing the split

Grouping by lake is necessary but not sufficient. A split derived from a seed silently moves whenever labels.csv changes — add a hundred labels and the test lakes are a different set, so no two results are comparable and a lake that was held out last week may be training data today. The fix is to compute the split once and commit the lake ids: 

splits/cloudytile_v1/
  train_ids.json   280 lakes
  val_ids.json      40 lakes
  test_ids.json     80 lakes
  split_meta.json

This is a 70 / 10 / 20 partition, matching the ESSD deposit's layout, and it is pinned for the life of the project. load_frozen_split raises on a lake it has never seen rather than silently dropping it, so a stale split fails loudly instead of quietly shrinking the evaluation set.

The 280 train and 40 val lakes together form the 320 dev lakes, and every decision — architecture, bands, learning rate, epoch, decision threshold — is made inside that pool. The 80 test lakes are read exactly once, by the final model.

5. The network

CloudyTileCNN (cloudytile/model.py) is a deliberately small CNN: three conv blocks — each conv 3×3 → BatchNorm → ReLU → maxpool /2 — then a global-average-pooling head, dropout 0.3, and a single logit (sigmoid → probability of "useful"). Input is a stack of one to six normalized bands. Training augments with flips and 90° rotations, which are exact symmetries here: a satellite tile has no canonical orientation.

That last point is the reason for the GAP head. A head that flattens the final feature block instead would size its first dense layer to the image area: at 256 px that is a 65,536-element vector, and at 512 px a 262,144-element one, giving dense layers of 8.4M and 33.5M weights respectively. The parameter count would then be set by a preprocessing choice rather than by any decision about model capacity, and it would change out from under you the moment the input resolution changed. Averaging instead makes the head 8,320 parameters at every resolution, which is why the config grid can be run at 256 px and the winner re-run at 512 px without touching the architecture.

Parameter counts across the grid

Adding input bands costs almost nothing — three extra channels is 432 weights in the first conv — because band count only touches one layer. Widening the conv stack is what actually changes capacity, and it is a 3.4× jump. Both are small enough that the whole grid fits comfortably on one GPU.

Two classifier heads

The conv stack turns a 512×512 tile into 64 channels of 64×64. The head's job is to get from that block to one number. How much of the block it keeps is a real modelling choice, and the two options differ only in one argument: how finely they pool.

Why the wider input costs so much more

That pooled block is flattened into a vector and fed to a fully connected layer — every input value gets its own weight to every hidden unit. So the weight count is not the number of inputs, nor the number of hidden units, but their product:

Which is why the hidden width has to shrink when the head widens. The same pool16 block behind a 128-unit layer would rebuild the problem the GAP head was adopted to solve:

6. Baselines any model must beat

Fit on the 320 development lakes and scored on the 80 frozen test lakes (2,000 frames, 67.5% useful) — the same lakes, and the same fit-then-score discipline, as the final model:

baselineaccuracywhat it knows
majority class ("always useful")67.5%nothing
JPG file-size threshold (44 KB)82.2%one byte count per image

The file-size baseline works because JPEG compression is an entropy meter: clear ice is detailed and compresses poorly, cloud is smooth and compresses well (cloudytile/splits.py::filesize_baseline). Any reported CNN accuracy should be quoted against 82.2%, not against chance — the interesting margin is what the network earns above a stat() call. Scene-level eo_cloud_cover metadata, for comparison, is nearly uninformative about per-tile usability and in 2019 actually ran backwards against human judgment.

The threshold is fit on the development lakes and applied to test, for the same reason model selection is kept off the test lakes: a threshold tuned on the data it is scored on flatters the baseline, which would understate the model's true margin. Reproduce with engine/run_baselines.py; the result is committed at splits/cloudytile_v1/baselines.json, so the number has provenance and moves only when the split does.

7. Choosing a model without cheating

Lake-grouping fixes how data is divided. It says nothing about a second leak, which is easier to miss: if you train 32 configurations and keep the one that scored best, the winner's score is partly a measure of luck, and the data those scores were computed on has been used to make a decision. That data is no longer a clean test set — it is training data for the selection step.

What a fold is

A single train/test split produces one number, and nothing to say how much of that number was luck. k-fold cross-validation produces k numbers instead. Divide the lakes into k equal parts — each part is a fold — then train k separate times. Each time, one fold is held out and scored, and the other k−1 are trained on. Every lake ends up held out exactly once, by a model that never saw it.

Both numbers matter. The mean is the configuration's score. The spread says how far that score moves on luck alone — because each fold holds out a different set of lakes, and some draws happen to contain more genuinely ambiguous frames than others. A gap between two configurations smaller than the spread is not a result.

Choosing k

The number of folds is a trade, not a free parameter:

kheld out per foldtrained onstd. error of the mean
3~107 lakes213 lakesspread / √3 = 0.0021
564 lakes256 lakesspread / √5 = 0.0017

More folds makes each individual estimate noisier, since fewer lakes are held out — but you average more of them, and every model trains on more data. The net effect is a tighter estimate of the configuration's true score. The config grid runs at k = 3, which is enough to answer coarse questions like "do extra bands help" across 32 configurations cheaply. The finalist rerun uses k = 5, because by that point the remaining question is a near-tie between a handful of configurations and precision is exactly what is missing.

One consequence to keep straight: a k = 3 score and a k = 5 score are not comparable. They are means over different partitions with different held-out sizes. Configurations are only ever ranked against others scored on identical folds — which they always are, because folds are a function of (labels, n_folds, seed) and nothing about the configuration.

A naming trap. Each result JSON carries test_auc, n_test_lakes and friends. Those describe that fold's held-out lakes, drawn entirely from the 320 development lakes — not the frozen 80 test lakes, which appear in no fold and are read only by the final model. A fold reporting n_test_lakes: 64 has held out 64 of the 320, and the 80 remain untouched.

The grid

32 configurations — 4 band sets (rgb, rgb+nir, rgb+swir16, all6) × 2 widths × 2 learning rates × 2 optimizers — each scored on 3 identical lake-grouped folds. The folds are a function of (labels, n_folds, seed) alone, so two configurations always differ by architecture, never by data.

The central question is the band question: does anything beyond true colour help a human-defined usability call? There is a physical reason to think so. The band statistics show SWIR varying far more than the visible bands — coefficient of variation above 1.0, against 0.20–0.23 — and that dynamic range is exactly what could separate cloud from bright ice, which look alike in RGB.

Everything else is held fixed — GAP head, BatchNorm, dropout 0.3, augmentation, 40 epochs, batch 32, and 256×256 input. The grid can run at 256 for roughly 4× the throughput precisely because the GAP head made the model resolution-independent; the winner can be re-run at 512 afterwards if resolution turns out to matter.

Reading the table

Configurations are ranked by AUC, not accuracy. Accuracy sits near the 67.5% majority rate, which compresses real differences, and it depends on a threshold — ranking by it would compare operating points and models at the same time. AUC is threshold-free.

The number that makes the table readable is the fold-to-fold spread. Each configuration is three numbers, and the standard deviation across them says how much of any apparent gap is noise. --summarize prints the ranked table and warns when the gap between first and second place is smaller than that spread — in which case the honest reading is a tie, and the rule is to take the simpler configuration rather than the nominal winner. A config that wins by less than its own run-to-run variation has not been shown to be better than anything.

The operating point

The dataset is 68.6% useful to 31.4% not useful — about 2.2:1, which is mild. That does not call for focal loss or class weights; plain BCEWithLogitsLoss is correct, and StratifiedGroupKFold already keeps label proportions even across folds.

What is lopsided is the cost of the two errors:

errorconsequence
false positive (cloudy called useful)a bad frame enters lake-vision's timeseries and can corrupt a drainage call
false negative (clear called cloudy)one observation lost from a lake that has ~90 usable ones

So precision on the useful class is worth more than recall — and the lever for that is the decision threshold, not the loss function. Tuning the threshold on validation probabilities keeps one training run yielding the entire precision/recall curve, leaves the operating point a single reportable number, and lets it be changed later without retraining anything. 

--threshold_objective f1                                        # default, balanced
--threshold_objective target_precision --target_precision 0.97  # cost-asymmetric

The full protocol, including what is deliberately not done (nested CV, cross-year evaluation), is in docs/CROSSVAL.md.

Extract frames for labeling (Sherlock)

Label (local browser GUI)

# left arrow = 0 not useful | right arrow = 1 useful
# backspace = back one frame | space = forward | h = help with examples
# writes labels/labels.csv atomically after every keypress; resume is automatic

Freeze the split (once, before any model is fit)

python3 engine/make_splits.py --labels_csv labels/labels.csv \
    --out_dir splits/cloudytile_v1
# writes train/val/test lake-id JSONs; commit them

Extract training tiles (Sherlock)

# JPGs are for labeling only; training reads per-tile 6-band .nc
sbatch slurm/extract_training_nc.sh
sbatch slurm/compute_band_stats.sh

Select a configuration (Sherlock)

sbatch slurm/run_cv_grid.sh          # 32 array tasks, 4 concurrent GPUs
python3 engine/run_cv_grid.py --out_dir <results> --summarize
# --split_dir restricts folds to the 320 dev lakes, so selection
# never sees the 80 test lakes. Each (config, fold) writes one JSON
# and existing ones are skipped, so a timed-out array can be resubmitted.

wandb sync <wandb_dir>/offline-run-*    # from a LOGIN node; compute nodes have no internet

Train the final model (Sherlock)

python3 engine/run_training.py \
    --labels_csv labels/labels.csv \
    --split_dir splits/cloudytile_v1 \
    --nc_dir /oak/.../data/cloudytile/training_nc_10k \
    --band_stats /oak/.../data/cloudytile/band_stats_10k.json \
    --nc_channels red green blue nir \
    --optimize_metric loss --save_path best_model.pth
# the only run that touches the 80 test lakes. Test metrics are computed on the
# restored best-validation checkpoint -- the same weights written to --save_path --
# at a threshold chosen on the validation lakes.

Inference over the lake archive

from cloudytile.inference import process_directory
process_directory(nc_dir=..., model_path="best_model.pth",

9. The rules this repo runs on

Nine constraints shape everything above. If you change one, change it deliberately.

  • Split by group, not by sample. Whenever samples are correlated — here, frames of the same lake — the group is the unit of independence. The guard is one assert; without it the leak is invisible and every score is inflated.
  • Freeze the split, don't seed it. A seed-derived split moves every time the label file grows, so two results are never comparable. The lake ids are committed.
  • Selection is training. Picking the best of 32 configurations consumes the data you picked on. The 80 test lakes are held back from every comparison for exactly that reason.
  • Report the dumb baseline, on the same holdout. A stat() call reaches 82.2%. A margin measured against a baseline scored on different lakes is not a margin at all.
  • A win smaller than the noise is not a win. Quote the fold-to-fold spread beside the mean, and inside that spread prefer the simpler model.
  • Metrics must describe the artifact. The test pass runs on the restored best-validation checkpoint, so the printed numbers describe the weights that actually ship.
  • Keep the head resolution-independent. Global average pooling means parameter count is a design decision rather than a side effect of the input size.
  • Order matters in preprocessing. Normalize, then fill no-data. The other order encodes "missing" as an extreme value that correlates with the label.
  • Label many groups shallowly rather than few groups deeply: 400 lakes × 25 frames generalizes far better than 60 lakes × 35 at the same labeling cost.
